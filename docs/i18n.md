# Languages (fa / en / tr / ru / ar) — how they work and how to keep translations in sync

Persian is the primary language and keeps every existing URL. English lives under `/en`, Turkish
under `/tr`, Russian under `/ru` and Arabic under `/ar` (`/ar`, `/ar/products/...`, `/ar/magazine/...`, `/ar/services/...`, `/ar/about`, `/ar/contact`).
Arabic is right-to-left, like Persian. English, Turkish and Russian are left-to-right.
Product URLs keep the Persian slug (`/products/<slug>` ⇄ `/en/products/<slug>` ⇄ `/tr/products/<slug>` ⇄ `/ru/products/<slug>` ⇄ `/ar/products/<slug>`),
so the toggle, hreflang and sitemap map one-to-one (translated product objects carry `slugName`, the
Persian name, for this). Every page has `<html lang dir>`, a self-canonical for its language, and
`hreflang` fa / en / tr / ru / ar / x-default (x-default = Persian; a language is omitted when that page has no
complete translation). The header FA / EN / TR / RU / AR switch links to the equivalent page.

Turkish, Russian and Arabic use the same files as English, under `src/i18n/tr/`, `src/i18n/ru/` and `src/i18n/ar/`, with the same Persian keys. Admin
editors that store `translations.en` also store `translations.tr`, `translations.ru` and `translations.ar`; that overlay wins over the
dictionary for that language only. A product or article that is not fully translated is not published
on `/tr`, `/ru` or `/ar`.

## Where the English lives

All English is keyed by the **exact Persian source text** (trimmed), so an edited Persian string
automatically stops matching and is reported as missing/stale.

| File | Contents |
| --- | --- |
| `src/i18n/en/ui.json`, `src/i18n/tr/ui.json` and `src/i18n/ru/ui.json` | UI strings used through `t("…")` / `tf("…")` in code. Typed against the English file: a `t()` key with no English entry fails `npm run lint`. Turkish and Russian must use the same keys. |
| `src/i18n/en/site.json`, `src/i18n/tr/site.json` and `src/i18n/ru/site.json` | Site data: company info, categories, enabled services, heroes, landing cards, topics, alts. |
| `src/i18n/en/products.json`, `src/i18n/tr/products.json` and `src/i18n/ru/products.json` | Every visible text of every public product (name, descriptions, specs, details, SEO). |
| `src/i18n/en/magazine.json`, `src/i18n/tr/magazine.json` and `src/i18n/ru/magazine.json` | `{ articleId: { persianLine: translation } }` — every line/field of each published article. |

Fallbacks: a missing UI string shows Persian; a product or article that is not **fully** translated
is not published on `/en` (no URL, not in the sitemap; links fall back to `/en/magazine` or the
English products list). Persian pages never download the English dictionary.

Article markers keep their format in English: `[IMG|path|English alt]`, `[CTA|English text|/path]`,
markdown link targets stay the Persian path (`[text](/products/…)`, localised at render), and
`[PRODUCTS|ts-xxx:English spec label,…]` uses the English spec label from `products.json`.

## The rule: every Persian change ships with its English

1. Change Persian (code, `src/data/*`, or the CMS).
2. Run `npm run check:i18n` (add `-- --todo /tmp/todo.json` to get every missing string as `{fa: ""}`).
3. Add/replace the English in the matching `src/i18n/en/*.json` and delete stale keys it lists.
4. Re-run until it prints **`i18n: in sync`** (exit code 0, `"inSync": true` in `i18n-report.json`).
5. Commit Persian and English together, then push. (`AGENTS.md` makes this mandatory for agents.)

Magazine content comes from the live CMS API by default (`--magazine-file <json>` or
`--magazine-url <url>` to use another source, `--no-magazine` to skip). After deploy,
`npm run check:i18n -- --base https://www.toyooran.com` also fetches every `/en` URL in the sitemap
and checks the prerendered HTML for leftover Persian and banned terms (URLs and link targets are ignored).
Note: disabled pages are skipped, except the fit-out service workflow steps, which the home page HTML lists.

CI (`.forgejo/workflows/deploy.yml`, job `i18n-check`) runs it with `--warn --base https://www.toyooran.com`
after every deploy (exported from the clean clone, reusing an existing `node_modules`): it only prints a
warning and never blocks or fails the deploy.

## English copy rules (enforced by the policy check)

- Company: "Toyooran Sanat Pouya". Formal, third person — never "we / our / us".
- Never "farmer": use poultry producers / poultry houses / poultry farm.
- Write "jet heater"; "IMACHINE" only in the body of the `imachine-jet-heater` article (its English
  title and summary omit it, so cards and listings elsewhere stay clean).
- No product codes (ts-xxx), no competitor names, no Danfoss / MARAS / IP54 / Virgin / "food grade".
- No project showcase. Feeder saving is 3–5 % only. Only the approved claims (the only butterfly pan
  manufacturer in Iran, 50 years, 200 projects, free consultation, university and IMACHINE collaboration).
- Phones: +98 911 511 6258 and +98 915 112 6258 (consulting, sales, support), office +98 51 3666 5600.
- Latin digits in English, Persian digits in Persian. Translate only what exists in Persian.

## Report (`i18n-report.json`)

`summary.inSync`, `missing` (ui / site / unwrapped literals / products / magazine), `stale`,
`untranslatedProducts`, `untranslatedArticles`, `policy` (rule violations) and `render` (with `--base`).
